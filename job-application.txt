JOB APPLICATION AUTOMATION SAAS
COMPLETE PROJECT REQUIREMENTS

1. PROJECT OVERVIEW

We are developing a SaaS-based job application automation platform for candidates applying to jobs in the United States.

The existing dice_apply.py Python script is the functional reference for the first job-platform integration. The current script automates job searching and applications on Dice using Playwright.

The new application should not simply convert the Python script into a web application. The script should be used to understand the required job-search, filtering, duplicate-checking, match-score, resume-upload, and multi-step application workflow.

The long-term goal is to support multiple job portals, including:

- Dice
- ZipRecruiter
- Indeed
- Monster
- Additional portals in the future

Dice will be the first supported platform. The architecture must allow additional job portals to be added without rewriting the core application.

The primary backend technology will be Node.js. The remaining technology stack can be finalized later.

3. US-ONLY PLATFORM

The platform is intended only for US job applications.

The system should restrict location selection to the United States.

Candidates should be able to select:

- US cities
- US states
- Multiple US locations
- Remote — United States

Non-US locations should not be allowed.

Potential fields include:

- Full Name

- Other standard candidate information required by supported job portals

The exact fields can be finalized based on the application requirements of each platform.

The candidate should not need to repeatedly enter the same basic information for every job application.


5. RESUME / CV MANAGEMENT

Resume management is a core part of the platform.

The existing Python script supports multiple roles and a CV associated with each role.

The SaaS application must support this behavior.

A candidate should be able to use:

Option A:
Different resume for different roles.

Example:

Business Analyst
→ Business Analyst Resume.pdf

Data Analyst
→ Data Analyst Resume.pdf

Option B:
The SAME resume for multiple roles.

Example:

Business Analyst
→ General Resume.pdf

Business Data Analyst
→ General Resume.pdf

Associate Business Analyst
→ General Resume.pdf

Therefore, assigning a resume to a role should NOT require uploading a new resume for every role. A previously uploaded resume should be selectable for multiple roles.

Resume functionality should include:

- Upload resume
- View uploaded resumes
- Replace/update resume
- Delete resume
- Assign any uploaded resume to one or more job roles
- Select which resume should be used for a particular application

The architecture should support multiple resumes per candidate.

13. DUPLICATE APPLICATION PREVENTION

Duplicate prevention is a critical requirement.

Before applying to a job, the system should check whether the candidate has already processed/applied to that job.

A job should preferably be identified using:

Platform + External Job ID

The job URL can also be stored as supporting information.

The database should prevent duplicate application records.

The system should also verify the current job status where possible because an old local application record can become stale.


14. JOB MATCH SCORE

The current Dice script reads Dice's own match score from the job detail page.

Example:

Your Dice Job Match score is 76%.

For the MVP, when a job portal provides its own match score, the system should store and use that platform-provided score.

Later, the SaaS can introduce a common AI-powered resume/job matching score so jobs from different platforms can be evaluated consistently.

Therefore, the system should keep these concepts separate:

- Platform Match Score
- Internal/AI Match Score

The initial implementation can use the platform-provided score where available.


15. MATCH THRESHOLD

The candidate should be able to configure a minimum match percentage.

Example:

Minimum Match Score: 70%

If the job score is:

82% → Continue with application

55% → Skip the job

The current Dice script already supports this behavior.

Jobs below the configured threshold should be skipped and recorded with a reason.


16. JOB SKIP REASONS

Every skipped job should have a clear reason.

Possible reasons:

- Match score below threshold
- Already applied
- Duplicate job
- Job no longer available
- Location mismatch
- Employment type mismatch
- Application not supported
- User-defined filter mismatch

The application history should preserve the skip reason.

The SaaS must support multi-step forms.

IMPORTANT REQUIREMENT — REQUIRED VS OPTIONAL FIELDS

The application must distinguish between MANDATORY fields and OPTIONAL fields.

Mandatory candidate/contact information must not be skipped.

For example, if the application requires:

- Email Address
- Phone Number
- Full Name
- Other mandatory contact information

the bot must provide those values and should NOT offer the user an option to skip them.

The system should maintain a mapping of required fields and candidate profile data.

Example:

Email Address
Required → YES
Candidate data available → YES
Action → Fill automatically

Phone Number
Required → YES
Candidate data available → YES
Action → Fill automatically

Full Name
Required → YES
Candidate data available → YES
Action → Fill automatically

Cover Letter
Required → NO
Candidate data available → NO
Action → Skip

OPTIONAL FIELDS

For optional fields, the system should allow the candidate to choose whether the bot should fill or skip them.

Examples:

- Cover Letter
- Optional message
- Optional portfolio URL
- Optional social profile
- Other non-mandatory fields

The user should have a configuration such as:

Optional Fields:
[x] Skip Cover Letter
[x] Skip Optional Message
[x] Skip Portfolio
[ ] Fill LinkedIn Profile

However, the bot must never skip a field that is actually mandatory for submission.

CORE RULE:

Mandatory field → MUST be completed.

Optional field → MAY be skipped according to candidate preference.

The automation should first determine whether a field is required based on the form's UI/validation state and available labels/attributes. If the field is mandatory, the bot must attempt to populate it using the candidate profile data.

If a mandatory field cannot be completed because required information is missing, the application should fail gracefully and record the exact reason rather than submitting incomplete information.

Example:

Email:
Required → YES
Value → candidate@email.com
Action → Fill

Cover Letter:
Required → NO
Value → Not provided
Action → Skip

This logic should be part of the generic application engine, while the individual portal adapter handles platform-specific form structures.


19. RESUME UPLOAD

The resume assigned to the current role should automatically be used during the application.

If the candidate has:

Business Analyst → Resume A
Business Data Analyst → Resume A
Associate Business Analyst → Resume B

the bot should automatically select the appropriate resume based on the role.

The system should identify resume upload fields and avoid treating optional cover-letter upload fields as resume fields.

If the resume upload itself is mandatory, the bot must upload the configured resume.

21. FAILURE HANDLING

A single failed application should not stop the entire bot.

Example:

Possible failure reasons:

- Login failure
- Authentication expired
- Job unavailable
- Apply button unavailable
- Application form changed
- Mandatory information missing
- Resume upload failure
- Website error
- Timeout
- Unexpected application step
- CAPTCHA or other platform interruption

The system should log the failure and continue where possible.

42. SECURITY REQUIREMENTS

Because the platform handles candidate information, resumes, and potentially job-portal credentials, security must be designed from the beginning.

Requirements:

- Passwords must not be stored as plain text.
- Sensitive credentials should be encrypted when storage is required.
- Resume files must have controlled access.
- Users must only access their own data.
- Authentication sessions/tokens must be protected.
- API endpoints require authorization.
- Logs must not expose passwords or sensitive credentials.
- File uploads must be validated.
- Database access should follow least-privilege principles.

The first development milestone should be:

"A web-based SaaS dashboard where a candidate can configure multiple job roles, assign the same or different resumes to those roles, select US-only job preferences, configure mandatory/optional application-field behavior, connect their Dice account, start an automated Dice job-application run, and monitor applied, skipped, and failed jobs in real time."

Once this works reliably, the second major milestone should be adding another job portal without changing the core dashboard, database, or automation workflow.

The architecture should prove that adding a second platform is primarily an adapter/integration task rather than a rewrite of the application.
